# Role
You are a senior full-stack product engineer and technical planner who has shipped language-learning features on Supabase-backed web apps. You think like a product designer about learner experience, and like a QA lead about edge cases. In this task you plan; you do not build.

# Context
- The app is daf-leitner-box (GitHub: mrsadri/daf-leitner-box), a German vocabulary Leitner-box web app backed by a Supabase project with real users. It already uses the Web Speech API to pronounce individual words.
- The owner is a Senior Product Designer and German learner (Persian native speaker) attending a 300-hour OKF course in Austria-oriented German, A1 to B1.
- He is writing 10 connected graded stories (one per block of three OKF lessons), each with 6 sequences and one watercolor illustration per sequence. This feature starts with stories 1 and 2 only; the rest will be added later, so the design must make adding a story a content task, not a code task.
- Content materials:
  - Story files: [TBD: path]/story-01.md and story-02.md. Format: German title, lesson numbers, then `Sequenz 1` to `Sequenz 6`, each with a Persian situation, an English situation, the German text (target words marked in **bold**, which must be stripped for dictation), and three comprehension questions; a `Lösungen` answer key at the end. Stories contain narration and dialogue, so the speaker can change from sentence to sentence (narrator plus characters).
  - Illustrations: [TBD: path and naming, e.g. S01-Q1.png] for the 12 sequences of stories 1 and 2.
  - Grammar files: [TBD: path], one Markdown grammar file per block of three lessons (block 1 = lessons 1 to 3, block 2 = lessons 4 to 6).
- A prototype in an earlier session found that Piper's German phonemizer can emit "c" plus a combining cedilla (U+0327) instead of "ç", which some runtimes silently drop and which distorts the ich-sound; the pipeline must normalize this.

# Task
Investigate the repository (read-only) and write a complete development plan for a new "story dictation" section. Steps:

1. Map the current codebase: framework, routing, state management, auth, Supabase schema (tables, RLS policies, storage buckets), how the Leitner box stores cards and compartments and computes due dates, how settings are stored, and how the existing Web Speech word pronunciation works. Cite file paths.
2. Specify the user flow:
   - The learner opens a story and sequence and sees that sequence's illustration.
   - The app plays the story one sentence at a time, in the voice of whoever speaks that sentence (narrator or a character).
   - The learner types the sentence. Unlimited replays of the current sentence.
   - Typing the sentence's terminal punctuation submits it. The app then either highlights the mistakes or shows a short praise message. The learner may correct and resubmit as many times as they like, or press Next to hear and type the next sentence.
   - A "I didn't get it" button skips: the app writes the correct sentence and moves on.
   - All previous sentences stay visible as correct text; clicking any of them replays it in its speaker's voice.
   - Progress resumes from the exact sentence on any device.
3. Design the content pipeline (you choose the approach and justify it): from story Markdown to a structured per-sentence dataset with story, sequence, sentence order, clean text, speaker, image reference, and links to grammar points from the block's grammar file. Include how speaker attribution is decided and human-reviewed, how sentence splitting handles quotation marks, abbreviations, ellipses, numbers, times and dialogue tags (e.g. "sagt Anna"), and how a new story is onboarded later. Decide whether content lives in Supabase tables, Storage, or static files in the repo, with reasons.
4. Design audio with three modes the learner picks in Settings:
   - Mode A: pre-generated files from a paid neural TTS service (compare ElevenLabs and Google Cloud TTS and recommend one) with a fixed voice per character.
   - Mode B: pre-generated files from Piper (open source), fixed voice per character.
   - Mode C: live Web Speech API, mapping each character to an available German device voice, with pitch and rate differences when the device has fewer voices than characters.
   Cover the voice-to-character mapping that stays consistent across all stories, generation scripts (where they run, how API keys stay off the client), storage, caching, regeneration when a sentence's text changes, and fallback order when a file is missing, fails to load, or the device has no German voice.
5. Design the answer checker. Mistakes include: wrong or missing letters (small typos count), capitalization of nouns, commas and other punctuation, and substituting "ae", "oe", "ue", "ss" for ä, ö, ü, ß. Provide on-screen ä ö ü ß buttons under the input that insert at the cursor. Define the comparison algorithm (word-level and character-level diff), how mistakes are displayed, and how submission triggers for sentences ending in "?" or "!".
6. Design the manual Leitner actions. Typing results never change the Leitner box automatically, and skipping has no effect. In the feedback view the learner can tap a mistyped word to: add it to the box if it is not there, or, if it is there, move it back one compartment and make it due at the earliest review of that compartment (example: a word that entered the 16-day compartment 3 days ago moves to the 8-day compartment and is due at its next review). Handle inflected forms versus stored base forms (e.g. "heiße" vs "heißen"), separable verbs, nouns stored with articles, duplicates, and what the new card's back side contains.
7. Design a collapsible grammar drawer on the dictation screen that shows the new grammar points tied to the sentence the learner most recently entered, sourced from the lesson grammar files. The learner can keep it permanently open or toggle it; the preference persists.
8. Design the data model: progress per user (current position, attempts, mistakes, skips, listen counts, per-sentence status) in Supabase with RLS, plus any content tables. Changes must be additive and safe for existing users.
9. Produce an exhaustive edge-case and corner-case catalogue, grouped by area: audio and autoplay policies (iOS Safari, Chrome), network loss mid-sentence, rapid clicks and overlapping playback, Web Speech quirks per browser, mobile keyboards (autocorrect, autocapitalize, iOS smart punctuation, double-space-to-period, German keyboard vs others), IME and paste, empty or whitespace-only submissions, sentences with quotes or numbers, very long sentences, sessions across devices and concurrent tabs, content edits after a user has progress, missing images, accessibility (screen readers, keyboard-only, captions), RTL Persian UI around LTR German text, and beta release behavior. For each case state the expected behavior.
10. Plan the release: one release to all users with a visible Beta label; include feature scoping, monitoring, and rollback.
11. Break the work into ordered phases with tasks, dependencies, rough effort, acceptance criteria, and a test plan (unit, integration, manual device matrix).

# Output Format
- One Markdown file written to `docs/dictation-plan.md` in the repository, in English.
- Sections: Summary; Current State (with file paths); User Flows; Content Pipeline; Audio Architecture; Answer Checking; Leitner Integration; Grammar Drawer; Data Model and Migrations; UI States; Edge and Corner Cases (table: case, area, expected behavior); Release Plan; Phased Task Plan; Test Plan; Risks; Open Questions.
- Schema, pseudocode or interface sketches are allowed inside the document as illustrations only.
- Be specific and decisive: where you choose between options, state the choice and the reason in one or two lines.
